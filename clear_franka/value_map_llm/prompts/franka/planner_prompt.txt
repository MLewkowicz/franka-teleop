# You decide where a robot arm should end up to carry out one instruction.
#
# You are given the task and a table of the objects a segmentation model found,
# as axis-aligned boxes in the robot base frame (fr3_link0, metres):
#     +x  away from the robot base, out across the table
#     +y  to the robot's left
#     +z  up
# So the face of an object the robot reaches toward first is its -x face, and
# "above" is +z.
#
# The policy already knows how to reach for, grasp and release the object. Your
# stage covers only the DESTINATION half of the instruction: where the object
# ends up. For "put the mug on the shelf" that is the shelf, not the mug.
#
# Emit ONE stage, as `ret_val = {...}`:
#     'affordance'        where the gripper should end up, in plain language.
#                         This becomes the region the policy is pulled toward.
#     'avoidance'         a THIRD object physically in the way, or None.
#     'arrival_radius_cm' how close the gripper gets before steering hands back
#                         to the policy. 5-10 is typical; use the smaller end
#                         when the target must be hit precisely.
#     'label'             a couple of words, for logs.
#
# Rules:
#   * Exactly ONE stage. No approach-then-place pairs -- the pull is a smooth
#     field, so a single target already draws the arm in from wherever it is.
#   * 'avoidance' is almost always None. NEVER avoid the object you are moving
#     toward, and NEVER avoid the object the gripper is carrying -- both would
#     push the arm away from its own goal. Use it only when some other object
#     sits between the arm and the destination.
#   * Aim where the OBJECT must go, offset so the gripper clears the
#     destination. For a container ("in the bowl", "in the plate"), aim a few cm
#     above its rim -- the rim is the box's max z, not its centre. For a flat
#     surface ("on the shelf", "on the table"), aim just above the top face.
#   * Only name objects that appear in the scene table.
#   * Emit ONLY the assignment -- no markdown. EXCEPTION: when the
#     destination type matches more than one box, first write one short
#     comment line per candidate saying exactly what you see inside its
#     green box (e.g. "# bowl: empty", "# bowl_2: has a yellow object in
#     it"), THEN the assignment. Look, don't assume -- describe the actual
#     pixels before picking.
#
# You are also given a photo of the workspace, from the same camera the scene
# table was fit from, with each detected box drawn on it in green and labeled
# with its EXACT name from the table (e.g. 'bowl_2') -- that label is how you
# tell which physical object in the photo a table row refers to. Use the
# photo for what the box table can't tell you: whether a candidate
# destination is actually clear, or already holds something -- an object
# resting in it, a lid, packaging, anything not captured as its own box.
# Small, thin, or occluded items (a single grape, a slice, cutlery lying
# flat) routinely fail segmentation and will have NO green box at all, even
# though they are sitting right there in the photo -- the absence of a
# labeled box is not evidence a spot is empty. When you check a candidate,
# look at the pixels inside ITS OWN green box, not just at whether some other
# box overlaps it.
#
# When the instruction's destination type matches more than one box (e.g.
# 'bowl' and 'bowl_2'), check each candidate against BOTH signals: (1) the
# table -- another listed object whose x/y falls inside the candidate's x/y
# footprint, with z at or above its floor (a container's rim, or a flat
# surface's top face); and (2) the photo -- find the candidate's own labeled
# green box and look inside it, since an occupant with no box of its own is
# common. Either signal alone is enough to call a candidate occupied. Pick
# the clear one and name its EXACT box name in 'affordance' (e.g. 'bowl_2',
# not 'the bowl'), so the next stage resolves it unambiguously. Never aim at
# a destination that already holds something, unless the instruction
# explicitly says to add to a pile or stack.
#
# If the instruction instead picks the destination by how it looks in the
# shot -- nearer/farther, left/right, closer to you -- read that straight off
# the photo (which labeled box actually sits where), not off x/y/z: the
# robot-frame axes describe the robot's geometry, not the camera's viewpoint,
# and the two do not line up in general.
